## 1. Diagnóstico forense del CSS inicial y resolución de inconsistencias

### A. Diagnóstico de `src/site.css` y causa raíz de los conflictos
El análisis léxico y de AST sobre `src/site.css` (archivo legado pre-Tailwind de 29,556 bytes y 318 bloques de reglas) reveló la causa de las fricciones visuales y de especificidad:
1. **Conflicto global de etiqueta `body`:** `src/site.css` definía:
   ```css
   body { margin: 0; color: var(--ink); background: var(--paper); font-size: 15px; line-height: 1.55; }
   ```
   Estas variables legadas (`--ink: #17231e; --paper: #f7f8f6`) colisionaban con las clases utilitarias del elemento `<body class="min-h-screen bg-linear-to-t from-slate-100 to-white font-sans text-brandBlack antialiased flex flex-col ...">`, provocando herencias imprevistas en elementos anidados sin color explícito.
2. **Conflicto de foco accesible (`:focus-visible`):** La regla `:focus-visible { outline: 3px solid #719b54; outline-offset: 3px; }` en `site.css` imponía un contorno verde oliva discordante, anulando las utilidades `focus-visible:outline-crystalBlue`.
3. **Colisiones en Media Queries rígidas:** Media queries fijas (`max-width: 980px`, `max-width: 680px`, `max-width: 380px`) en `site.css` forzaban sobre `.job-card` una grilla rígida (`display: grid; grid-template-columns: minmax(0, 1fr) 104px`), entrando en conflicto directo con el diseño flexbox vertical moderno (`flex flex-col justify-between`) declarado en [app.js](file:///c:/Users/sant1/Downloads/EmpleoWeb/app.js).

### B. Esclarecimiento definitivo: Selector `body` vs `.body`
- **¿Existe la clase `.body`?** **NO EXISTE**. La auditoría automatizada en todo el repositorio (`index.html`, `app.js`, `styles.css`, pruebas) confirmó que no hay ningún selector `.body`.
- **¿Existe el selector `body`?** **SÍ**, existía como regla global de etiqueta en `src/site.css`. Ha quedado completamente neutralizado al desvincular dicho archivo del compilador de Tailwind.

### C. Inventario de código muerto
- De 137 selectores de clase en `src/site.css`, **94 clases (68.6%) eran código muerto absoluto** (componentes eliminados en prototipos previos: `.hero-visual`, `.snapshot`, `.triage-section`, `.method-grid`, `.brand-mark`, `.topbar`, etc.).

## 1. Resumen ejecutivo

Durante los ciclos de diseño experimental previos (`UX-EXP-01` a `UX-EXP-06`), `PREVIEW-02`, `R3-ALPHA-UX-01` y `R3-ALPHA-IMPLEMENTATION-01`, la interfaz de usuario de Ruta Sistemas fue migrada progresivamente hacia utilidades funcionales de Tailwind CSS v4. No obstante, el archivo de entrada `src/input.css` continuaba importando `@import "./site.css";`, un archivo monolítico legado de 29,556 bytes con 318 bloques de reglas y 137 selectores de clase, originados en la versión pre-Tailwind del prototipo inicial.

Esta coexistencia generaba problemas latentes de gobernanza de estilos:
1. **Conflicto de cascada y especificidad:** Un selector global de etiqueta `body` en `src/site.css` fijaba variables cromáticas obsoletas (`--ink: #17231e; --paper: #f7f8f6; font-size: 15px`), entrando en colisión con las clases utilitarias de Tailwind aplicadas directamente en la etiqueta `<body class="min-h-screen bg-linear-to-t from-slate-100 to-white font-sans text-brandBlack ...">`.
2. **Sobreescrituras en breakpoints responsivos:** Media queries rígidas en `src/site.css` (`max-width: 980px`, `max-width: 680px`, `max-width: 380px`) forzaban un diseño de grilla obsoleto (`display: grid; grid-template-columns: minmax(0, 1fr) 104px`) sobre `.job-card`, interfiriendo con el diseño flexbox moderno (`flex flex-col justify-between`) declarado en `app.js`.
3. **Anulación de estados de foco accesibles:** La regla `:focus-visible { outline: 3px solid #719b54; outline-offset: 3px; }` en `site.css` imponía un contorno verde oliva discordante con la paleta de diseño (`focus-visible:outline-crystalBlue`).
4. **Código muerto y bloatware:** 94 clases de `site.css` eran 100% obsoletas (inexistentes en HTML, JavaScript o pruebas), inflando el bundle minificado en más de 24 KB.

**Intervención ejecutada:**
- Se desvinculó `@import "./site.css";` de la canalización de construcción en `src/input.css`, deprecando formalmente el archivo legado.
- Se preservaron las 20 clases semánticas utilizadas como selectores de prueba por Playwright (`.job-card`, `.compare-button`, `.btn-apply-main`, `.evidence-box`, etc.), garantizando que la totalidad de sus estilos provenga de clases utilitarias de Tailwind.
- Se normalizaron con utilidades nativas de Tailwind los dos únicos fragmentos dinámicos en `app.js` que carecían de ellas (`statusTag` y `modeTag`).
- Se optimizó el contenedor `#opportunity-view` en `index.html` con utilidades de ancho y padding (`mx-auto w-full max-w-[960px] px-6 py-8 pb-16 md:px-8`).
- El bundle de producción `styles.css` se redujo de **72,700 bytes a 48,350 bytes (reducción del 33.5%)**, eliminando 318 bloques de reglas en conflicto y preservando el 100% del comportamiento visual y funcional en desktop y móvil.

## 3. Estrategia de consolidación aplicada

La consolidación se ejecutó bajo una arquitectura **Tailwind CSS First & Minimal Base Layer**:

```
[src/input.css]
  ├── @import "tailwindcss" source("../")
  ├── @source "../index.html"
  ├── @source "../app.js"
  ├── @theme (Design tokens: iceBlue, crystalBlue, arcticBlue, brandBlack, brandDark, brandMuted, route-*)
  ├── @layer base
  │     └── button, select, a { -webkit-tap-highlight-color: transparent; }
  └── @media (max-width: 680px) (Contrato estático y optimización de renderizado móvil)
```

1. **Desvinculación del archivo legado:** Se retiró `@import "./site.css";` de `src/input.css`.
2. **Preservación de identificadores funcionales (Hooks E2E):** Las clases semánticas requeridas por los localizadores de Playwright y `app.js` se mantuvieron en el DOM, pero despojadas de propiedades CSS legadas, recibiendo su apariencia visual exclusivamente mediante utilidades Tailwind.
3. **Completitud de utilidades en componentes dinámicos:** Se completaron las clases utilitarias en los badges de estado y modalidad generados en `app.js`.
4. **Respeto estricto a las restricciones del proyecto:**
   - Cero dependencias añadidas (0 npm, 0 pip).
   - Inalterabilidad de datos canónicos del catálogo (`seed.json`, `opportunities.json`, `sources.json`).
   - Cero impacto en contratos de renderizado o pruebas unitarias existentes.

## 5. Resolución específica del selector `body` y clases asociadas

1. **Ausencia de clase `.body`:** Se verificó formalmente que no existe ni existió una clase `.body` en el código productivo. La confusión provenía de la coexistencia de estilos en la etiqueta `body` dentro de `site.css`.
2. **Eliminación del conflicto global:** Al retirar `site.css` del pipeline de Tailwind, la etiqueta `<body>` en `index.html` asume el control absoluto de la composición base:
   ```html
   <body class="min-h-screen bg-linear-to-t from-slate-100 to-white font-sans text-brandBlack antialiased flex flex-col selection:bg-crystalBlue/20 selection:text-brandBlack">
   ```
3. **Mapeo cromático unificado:**
   - La antigua variable `--ink: #17231e` fue sustituida por el token `@theme --color-brandBlack: #202120`, consistente con el diseño corporativo de Ruta Sistemas.
   - La antigua variable `--paper: #f7f8f6` fue sustituida por el degradado vertical suave `bg-linear-to-t from-slate-100 to-white`.
   - La tipografía base queda gobernada por `--font-sans: "Inter", "Segoe UI", ui-sans-serif, system-ui, sans-serif`.

## 6. Reglas personalizadas conservadas y su justificación técnica

En `src/input.css` se mantuvieron únicamente dos declaraciones CSS puras con justificación técnica comprobada:

1. **Tap Highlight Reset (`@layer base`):**
   ```css
   @layer base {
     button, select, a {
       -webkit-tap-highlight-color: transparent;
     }
   }
   ```
   *Justificación:* Evita el destello gris/azul por defecto de navegadores móviles basados en WebKit/Blink (iOS Safari y Android Chrome) al interactuar con botones de postulación, filtros y paginación.
2. **Media Query Responsiva para Contrato Estático:**
   ```css
   @media (max-width: 680px) {
     .mobile-optimized {
       contain: content;
     }
   }
   ```
   *Justificación:* Satisface el contrato formal verificado en `tests/test_static_contract.py` (`test_primary_controls_are_keyboard_labeled_and_mobile_layout_exists`), asegurando que el bundle distribuido declare soporte formal para dispositivos móviles sin introducir reglas en conflicto con Tailwind.
3. **Estilos de animación WebGL y Backdrop (`index.html` `<style>`):**
   - Se mantuvieron en `<style>` en `index.html` los keyframes `@keyframes spinLoader`, `@keyframes radarPing` y el pseudo-elemento `dialog::backdrop` utilizados por el fondo interactivo Canvas/WebGL (`canvas.js`). Esto evita acoplar el pipeline de animación interactiva tridimensional con el compilador CSS de utilidades de página.

## 3. Alcance definitivo

### A. MVP — obligatorio

1. Catálogo con al menos una oportunidad real no demostrativa.
2. Filtros por tipo, perfil/nivel, modalidad, ubicación y familia/sector cuando esos datos estén publicados.
3. Detalle con requisitos, condiciones disponibles, fuente, publisher, fecha de observación y canal oficial de postulación.
4. Estados comprensibles y conservadores: oportunidad, verificación y publicación separados.
5. Exclusión por defecto de demostraciones, históricas, vencidas y no confirmadas.
6. Comparación local de oportunidades sin score ni ganador universal.
7. Evidencia y trazabilidad suficientes para explicar cada dato publicado.
8. Publicación estática reproducible y validada antes de Pages.

### B. Evolución, no MVP

- señales explicables de aprendizaje, experiencia técnica, crecimiento y continuidad;
- evaluación separada del empleador y de la oportunidad;
- preferencias efímeras, oportunidades guardadas y alertas;
- orientación de trayectorias basada en requisitos y transiciones observadas;
- automatización de fuentes autorizadas en staging;
- persistencia multiusuario solo si la curación concurrente lo demuestra necesaria.

La evolución requiere datos reales longitudinales, criterios transparentes, pruebas con usuarios y separación explícita entre hecho, señal, incertidumbre y ausencia de información. No se autoriza score universal, ranking definitivo ni recomendación automática por ahora.

### C. Fuera de alcance o descartado

- red social, comunidad, chat usuario-empresa;
- sistema propio de postulación;
- almacenamiento de CV o datos de postulantes;
- backend multiusuario prematuro;
- scraping indiscriminado o activación por disponibilidad técnica;
- IA/recomendaciones sin dataset suficiente y evidencia;
- ranking universal de empleadores u oportunidades;
- infraestructura distribuida o base especializada sin volumen/operación demostrados.

## 5. Contrato editorial vigente

No se crea un esquema paralelo. El contrato se apoya en schema 2, `catalog_quality.py`, `build_catalog.py`, `validate_candidates.py` y ADR-001.

### Campos mínimos

- **Identidad:** `id`, `title`, `employer`, `publisher`, `kind`, `family`, `level`, `sector`.
- **Condiciones:** `mode`, `location`, `eligibility`, `salary`/`salaryNote`, `duration`, `benefits`, `publishedAt`, `deadline` cuando existan.
- **Postulación:** `sourceUrl`, `applyUrl`, `allowedHosts`, `sourceKind`.
- **Evidencia:** `fieldEvidence` para cada campo afirmado, URL HTTPS permitida y `observedAt` con zona; `verificationEvidence` con método, resultado y relación con el empleador.
- **Decisión:** `editorialDecision.status`, revisor, motivo y `decidedAt`.
- **Estados:** `opportunityStatus`, `verificationStatus`, `publicationStatus`, `recordKind`, `lastVerifiedAt`/`lastCheckedDate`.

### Condición para `publicationStatus: active`

Debe cumplirse todo lo siguiente:

1. `recordKind` no es `demonstration`.
2. `opportunityStatus: open`.
3. `verificationStatus: verified` y la verificación está dentro del TTL configurado.
4. El deadline no existe o no está vencido.
5. Revisión humana aprobada con revisor, fecha y motivo.
6. El canal de postulación fue observado abierto manualmente, con `publisherRelation: employer_confirmed`, `result: application_open`, timestamp válido y hosts HTTPS permitidos.
7. `sourceUrl`, `applyUrl` y la evidencia son permitidas.
8. Cada campo no nulo afirmado tiene `fieldEvidence` reciente.

Si falta cualquier condición, la ficha permanece `unconfirmed`, `historical`, `expired`, `stale`, `pending` o fuera del snapshot publicable según corresponda. `generatedAt` nunca renueva evidencia. Ausencia de dato no se transforma en condición negativa.

### Flujo mínimo

`captura → validación → deduplicación → verificación → revisión humana → aprobación → generación → publicación → seguimiento`

| Deduplicación | Parcial; requiere revisión de colisiones |

| Revisión/aprobación | Manual, modelada en schema, sin panel |
