## Escalabilidad del Catálogo (Paginación) y Presentación Estructurada de Contenido (Listas y Viñetas)

---

### 1. Resumen Ejecutivo de la Intervención

En respuesta a las observaciones formuladas por el propietario tras la evaluación de las nuevas oportunidades en la Alpha privada, se implementaron de forma nativa dos capacidades clave de interfaz:

1. **R3-ALPHA-UX-01A (Paginación escalable del catálogo):** Un mecanismo de paginación con límite de 12 tarjetas por página (`PAGE_SIZE = 12`). Cuando el catálogo filtrado contiene 12 o menos oportunidades (como en el estado actual de la Alpha privada), los controles permanecen completamente ocultos sin generar ruido visual. Cuando el catálogo supera las 12 tarjetas, se despliegan automáticamente los controles accesibles «Anterior» y «Siguiente» con el indicador `Página X de Y · Mostrando A–B de N oportunidades`, reseteo a página 1 ante cambios de búsqueda o filtros, navegación suave (`scrollIntoView`) y preservación íntegra de la selección en el comparador local.
2. **R3-ALPHA-UX-01B (Presentación estructurada de descripciones y listas):** Formateo semántico visual en listas con viñetas (`<ul class="list-disc pl-5 space-y-1.5 ..."><li>...</li></ul>`) para campos que representan listas delimitadas por punto y coma (`;`) en la fuente (`tasks` / "Qué harías", `requirements` / "Requisitos del puesto", `benefits` / "Beneficios publicados"), normalizando la puntuación final y capitalizando amigablemente cada viñeta. Se mantuvieron intactos como párrafos continuos (`<p>`) aquellos textos donde el punto y coma cumple función gramatical (`growth`, notas de procedencia y textos narrativos).

## 1. Contexto y Objetivos del Bloque

Tras la incorporación de las cinco nuevas oportunidades reales de Canonical Ubuntu a la Alpha privada en `R3-ALPHA-PROMOTION-01` (ampliando el catálogo a 11 fichas: 6 reales y 5 demostrativas), el propietario evaluó la aplicación y formuló dos inquietudes concretas sobre la experiencia de uso:

1. **Escalabilidad del catálogo:** ¿Cómo se comportará la interfaz cuando existan 20, 40 o más tarjetas de oportunidades laborales?
2. **Estructura y legibilidad de descripciones:** En los detalles del puesto, varios campos presentaban elementos agrupados en un solo bloque continuo separados por punto y coma (`;`), dificultando su escaneo visual en lugar de mostrarse como listas legibles con viñetas.

El objetivo de `R3-ALPHA-UX-01` es dar respuesta técnica a ambas inquietudes en el frontend sin introducir nuevas dependencias, sin romper contratos existentes y sin modificar en un solo byte los archivos de datos canónicos.

## 2. Implementación R3-ALPHA-UX-01A: Paginación Escalable del Catálogo

### 2.1 Reglas de Diseño y Límite por Página
- **Tamaño de página (`PAGE_SIZE`):** Se definió una constante de 12 tarjetas por página (`PAGE_SIZE = 12`).
- **Visibilidad condicional:**
  - Si el total de oportunidades visibles/filtradas es menor o igual a 12 (`totalJobs <= 12`), el contenedor de paginación (`#pagination`) permanece completamente oculto (`hidden = true`).
  - Si el total de oportunidades supera 12 (`totalJobs > 12`), el contenedor se despliega automáticamente mostrando controles de navegación y métricas de página.
- **Controles de navegación:**
  - Botón **Anterior** (`#prev-page`): Habilitado a partir de la página 2; deshabilitado en página 1 (`disabled = currentPage <= 1`).
  - Botón **Siguiente** (`#next-page`): Habilitado mientras queden páginas posteriores; deshabilitado en la última página (`disabled = currentPage >= totalPages`).
  - Indicador informativo (`#pagination-info`): Notificación contextual con formato `Página X de Y · Mostrando A–B de N oportunidades` con `aria-live="polite"`.
- **Navegación fluida:** Al cambiar de página mediante `goToPage(page)`, la vista ejecuta un desplazamiento suave (`scrollIntoView({ behavior: 'smooth', block: 'start' })`) hacia la lista de resultados para evitar que el usuario quede ubicado al pie de página.
- **Reseteo ante cambios de estado:** Todo cambio en los filtros de búsqueda (`#query`, `#location`, `#mode`, `#kind`, `#family`, `#sector`, `#level`, etc.), limpieza de filtros (`#clear-filters`, `#empty-clear`) o conmutación de ejemplos demostrativos (`#include-demonstrations`) o historial (`#include-history`) resetea automáticamente `currentPage = 1`.
- **Preservación del Comparador Local:** Las selecciones para comparación (`compareIds`) se almacenan en el estado desacoplado de la vista y se conservan intactas al navegar entre páginas. Una ficha seleccionada en la página 1 mantiene su estado `selected` y el panel de comparación flotante permanece consistente al pasar a la página 2.

## 3. Implementación R3-ALPHA-UX-01B: Presentación Estructurada de Listas

### 3.1 Detección Semántica y Formateo
Se implementó la función auxiliar `formatStructuredList(text, fallbackText)` en `app.js`:

```javascript
function formatBulletItem(item) {
  const clean = item.replace(/\.$/, '').trim();
  if (!clean) return '';
  if (/^[a-z][a-z0-9]/.test(clean) && !/^[a-z][A-Z]/.test(clean)) {
    return clean.charAt(0).toUpperCase() + clean.slice(1);
  }
  return clean;
}

function formatStructuredList(text, fallbackText = '') {
  if (!text || typeof text !== 'string' || !text.trim()) {
    return fallbackText ? `<p class="text-sm text-stone-700 leading-relaxed">${escapeHTML(fallbackText)}</p>` : '';
  }
  const trimmed = text.trim();
  if (!trimmed.includes(';')) {
    return `<p class="text-sm text-stone-700 leading-relaxed">${escapeHTML(trimmed)}</p>`;
  }
  const items = trimmed.split(';').map((item) => item.trim()).filter(Boolean);
  if (items.length <= 1) {
    return `<p class="text-sm text-stone-700 leading-relaxed">${escapeHTML(trimmed)}</p>`;
  }
  return `<ul class="list-disc pl-5 space-y-1.5 text-sm text-stone-700 leading-relaxed">${items
    .map((item) => `<li>${escapeHTML(formatBulletItem(item))}</li>`)
    .join('')}</ul>`;
}
```

### 3.2 Campos Transformados
1. **`job.tasks` ("Qué harías"):**
   - Textos con punto y coma (p.ej. OP-001, OP-002, OP-004, OP-005, OP-006 a OP-010) se renderizan como `<ul class="list-disc pl-5 ..."><li>...</li></ul>`.
   - Elementos con viñeta se despojan de puntos finales redundantes y se capitaliza la primera letra para legibilidad profesional.
2. **`job.requirements` ("Requisitos del puesto"):**
   - Convocatorias con requisitos múltiples separados por `;` (p.ej. OP-005 con 6 requisitos, OP-006 con 5, OP-008 con 6) se muestran con viñetas independientes.
3. **`job.benefits` ("Beneficios publicados"):**
   - Convocatorias con beneficios desglosados (p.ej. OP-006 con 5 beneficios: remoto 100%, USD 2,000 capacitación, viajes semestrales, bono, feriados) se muestran en viñetas claras.

### 3.3 Preservación Estricta de Textos Narrativos
- Textos sin punto y coma (p.ej. `QA-001` tasks: *"Práctica dirigida a la Jefatura de Contratos Portuarios."*) se preservan intactos como párrafos `<p>`.
- El campo `growth` ("Qué experiencia podrías llevar al siguiente paso") permanece estrictamente como párrafo narrativo `<p>`, respetando el uso gramatical y analítico del punto y coma editorial sin convertirlo en viñetas.
- Los campos de procedencia y notas analíticas no fueron perturbados.

Ruta Sistemas construirá primero un **catálogo estático, curado y verificable de oportunidades reales para perfiles iniciales y junior de Sistemas en Perú**, incluyendo oportunidades remotas solo cuando la elegibilidad desde Perú esté explícita. La arquitectura vigente se conserva: `data/opportunities.seed.json` como fuente canónica, snapshot generado, frontend estático, validación fail-closed y publicación portable. No se incorpora backend multiusuario, CMS, IA, scraping general ni nueva infraestructura antes de demostrar una necesidad concreta.

**Regla de cierre del MVP:** mientras no exista al menos una ficha real que cumpla el contrato editorial y pueda consultarse correctamente, el producto es un piloto técnico/editorial, no un MVP terminado.

## 3. Alcance definitivo

### A. MVP — obligatorio

1. Catálogo con al menos una oportunidad real no demostrativa.
2. Filtros por tipo, perfil/nivel, modalidad, ubicación y familia/sector cuando esos datos estén publicados.
3. Detalle con requisitos, condiciones disponibles, fuente, publisher, fecha de observación y canal oficial de postulación.
4. Estados comprensibles y conservadores: oportunidad, verificación y publicación separados.
5. Exclusión por defecto de demostraciones, históricas, vencidas y no confirmadas.
6. Comparación local de oportunidades sin score ni ganador universal.
7. Evidencia y trazabilidad suficientes para explicar cada dato publicado.
8. Publicación estática reproducible y validada antes de Pages.

### B. Evolución, no MVP

- señales explicables de aprendizaje, experiencia técnica, crecimiento y continuidad;
- evaluación separada del empleador y de la oportunidad;
- preferencias efímeras, oportunidades guardadas y alertas;
- orientación de trayectorias basada en requisitos y transiciones observadas;
- automatización de fuentes autorizadas en staging;
- persistencia multiusuario solo si la curación concurrente lo demuestra necesaria.

La evolución requiere datos reales longitudinales, criterios transparentes, pruebas con usuarios y separación explícita entre hecho, señal, incertidumbre y ausencia de información. No se autoriza score universal, ranking definitivo ni recomendación automática por ahora.

### C. Fuera de alcance o descartado

- red social, comunidad, chat usuario-empresa;
- sistema propio de postulación;
- almacenamiento de CV o datos de postulantes;
- backend multiusuario prematuro;
- scraping indiscriminado o activación por disponibilidad técnica;
- IA/recomendaciones sin dataset suficiente y evidencia;
- ranking universal de empleadores u oportunidades;
- infraestructura distribuida o base especializada sin volumen/operación demostrados.

## 5. Contrato editorial vigente

No se crea un esquema paralelo. El contrato se apoya en schema 2, `catalog_quality.py`, `build_catalog.py`, `validate_candidates.py` y ADR-001.

### Campos mínimos

- **Identidad:** `id`, `title`, `employer`, `publisher`, `kind`, `family`, `level`, `sector`.
- **Condiciones:** `mode`, `location`, `eligibility`, `salary`/`salaryNote`, `duration`, `benefits`, `publishedAt`, `deadline` cuando existan.
- **Postulación:** `sourceUrl`, `applyUrl`, `allowedHosts`, `sourceKind`.
- **Evidencia:** `fieldEvidence` para cada campo afirmado, URL HTTPS permitida y `observedAt` con zona; `verificationEvidence` con método, resultado y relación con el empleador.
- **Decisión:** `editorialDecision.status`, revisor, motivo y `decidedAt`.
- **Estados:** `opportunityStatus`, `verificationStatus`, `publicationStatus`, `recordKind`, `lastVerifiedAt`/`lastCheckedDate`.

### Condición para `publicationStatus: active`

Debe cumplirse todo lo siguiente:

1. `recordKind` no es `demonstration`.
2. `opportunityStatus: open`.
3. `verificationStatus: verified` y la verificación está dentro del TTL configurado.
4. El deadline no existe o no está vencido.
5. Revisión humana aprobada con revisor, fecha y motivo.
6. El canal de postulación fue observado abierto manualmente, con `publisherRelation: employer_confirmed`, `result: application_open`, timestamp válido y hosts HTTPS permitidos.
7. `sourceUrl`, `applyUrl` y la evidencia son permitidas.
8. Cada campo no nulo afirmado tiene `fieldEvidence` reciente.

Si falta cualquier condición, la ficha permanece `unconfirmed`, `historical`, `expired`, `stale`, `pending` o fuera del snapshot publicable según corresponda. `generatedAt` nunca renueva evidencia. Ausencia de dato no se transforma en condición negativa.

### Flujo mínimo

`captura → validación → deduplicación → verificación → revisión humana → aprobación → generación → publicación → seguimiento`

| Paso | Estado actual |
|---|---|
| Captura | Manual; automatización bloqueada |
| Validación | Implementada para candidatos, semilla y snapshot |
| Deduplicación | Parcial; requiere revisión de colisiones |
| Verificación | Manual y documentada; no existe ficha real aprobada |
| Revisión/aprobación | Manual, modelada en schema, sin panel |
| Generación/publicación | Implementada y fail-closed |
| Seguimiento/retirada | Política documentada; ejecución manual |

## 6. Criterios de aceptación congelados

### MVP

- [ ] Existe al menos una oportunidad real, no demostrativa, consultable y aprobada.
- [ ] Una persona puede filtrar, abrir el detalle, distinguir empleador/publisher y llegar al canal oficial.
- [ ] Una ficha vencida, stale o sin evidencia no aparece como activa por defecto.
- [ ] La comparación no produce score, ganador ni valores inventados.

### Datos y publicación

- [ ] `build_catalog.py --check`, `validate_catalog.py` y `validate_candidates.py` pasan.
- [ ] Cada dato afirmado tiene evidencia HTTPS y fecha válida; los desconocidos permanecen ausentes/null.
- [ ] La publicación falla si el esquema, host, fecha, estado o artefacto son inválidos.
- [ ] El artefacto contiene exactamente los archivos permitidos y no depende de CDN runtime.

### Experiencia e integridad técnica

- [ ] Prueba de navegador cubre carga, filtros, estado vacío/error, detalle, comparación y enlaces relativos bajo Pages.
- [ ] Prueba local cubre `canvas.js` o documenta su exclusión; no hay 404/MIME incorrecto.
- [ ] Se revisan teclado, diálogo, viewport móvil y `prefers-reduced-motion`.
- [ ] No se declara éxito remoto sin observar el artefacto y la URL desplegados.

### Evolución

- [ ] No se inicia scoring, alertas, trayectorias o personalización sin datos y protocolo de medición documentados.
- [ ] Una fuente nueva tiene autorización escrita separada para consulta, retención, atribución, retirada y republicación antes de cualquier solicitud.
- [ ] La automatización produce staging/candidatos y nunca promociona directamente a seed, snapshot o Pages.
