2. **Scripts y Módulos de Revalidación ([collector/revalidation.py](file:///c:/Users/sant1/Downloads/EmpleoWeb/collector/revalidation.py)):**
   - Implementada la función orquestadora `revalidate_canonical_catalog()` desacoplada del proceso de promoción de staging.
   - Taxonomía estandarizada de estados de respuesta:
     - `RESULT_OPEN_CONFIRMED`: Vacante activa y confirmada en la fuente oficial.
     - `RESULT_CLOSED_CONFIRMED`: Vacante confirmada explícitamente como cerrada o concluida.
     - `RESULT_DISAPPEARED_ONCE`: Primera ausencia detectada; vacante se mantiene activa (salvaguarda anti-cierre).
     - `RESULT_NOT_FOUND_CONFIRMED`: Segunda ausencia consecutiva confirmada; vacante pasa a histórica.
     - `RESULT_TEMPORARY_ERROR`: Error de red (HTTP 403, 429, 500, socket timeout o JSON corrupto); el contador de ausencias no se incrementa.
     - `RESULT_SOURCE_UNSUPPORTED`: Fuente sin conector automatizado; no se cierra la oportunidad.
     - `RESULT_UNKNOWN`: Oportunidad sin identificador externo deducible.

3. **Conectores Reutilizados:**
   - La función `fetch_board_data()` centraliza la consulta y reutiliza los adaptadores probados de:
     - Greenhouse API (`fetch_greenhouse_board` y `transform_greenhouse_payload`).
     - Lever Postings API (`fetch_lever_board` y `transform_lever_payload`).
     - Portales públicos CAS: OSITRAN (`fetch_ositran_convocatorias`) y Defensoría del Pueblo (`fetch_defensoria_cas`).
     - HiringRoom multitenant: UTP, Stefanini, Canvia, MyApps y Efitec (`fetch_hiringroom_board`).
     - Gob.pe / INDECOPI (`fetch_gobpe_convocatorias`).

4. **Persistencia de Estado ([data/revalidation-state.json](file:///c:/Users/sant1/Downloads/EmpleoWeb/data/revalidation-state.json)):**
   - El historial de consultas, timestamps de ausencias (`firstAbsentAt`, `lastAbsentAt`, `lastCheckedAt`) y el conteo de ausencias consecutivas se persisten en un archivo dedicado versionable y auditable.
   - Esto evita modificar o corromper el contrato Schema 2 de las fichas públicas visibles para el usuario final mientras garantiza que el conteo de ausencias sobreviva entre sesiones independientes de CI/CD.

5. **Tratamiento Riguroso de Ausencias Consecutivas:**
   - **Caso 1 ausencia:** El contador sube a 1, la oportunidad se conserva activa (`opportunityStatus: "open"`, `publicationStatus: "active"`).
   - **Caso 2 ausencias consecutivas:** El contador llega a 2, la oportunidad se marca como concluida (`opportunityStatus: "closed"`, `publicationStatus: "historical"`, `verificationStatus: "stale"`).
   - **Caso reaparición:** Si una vacante ausente reaparece en la siguiente corrida, el contador se reinicia a 0.
   - **Caso error intermedio:** Un fallo de red entre dos consultas exitosas no incrementa el contador ni reinicia el conteo previo; se preserva intacto.

## 1. Visión y Principios Rectores

### 1.1 Visión
Convertir a **Velora** en el catálogo nacional confiable de oportunidades profesionales para estudiantes, bachilleres, egresados y profesionales de **Ingeniería de Sistemas, Informática, Computación, Software, Ciberseguridad, Datos y Tecnología en el Perú**.

### 1.2 Principios Rectores de Ingeniería y Producto
1. **Verificabilidad Absoluta (*Fail-Closed*):** Ninguna oportunidad se publica sin evidencia de procedencia, enlace al canal oficial del empleador y confirmación de vigencia.
2. **Claridad sobre Promesas:** Velora no promete trabajo, ascensos ni continuidad; informa condiciones objetivas, modalidades contractuales y riesgos de forma explicable.
3. **OSS-First:** Priorizar herramientas abiertas y estándar (Python standard library, SQLite, Tailwind OSS, herramientas nativas) antes de incorporar servicios comerciales o frameworks pesados.
4. **Backend-less Ligero:** Mantener la distribución estática de alta disponibilidad y bajo costo, delegando la adquisición y validación a procesos locales o CI/CD reproducibles.
5. **No Exclusión por Nivel:** Los niveles formativos (Prácticas), Junior, Mid y Senior son facetas de filtrado para entender oportunidades, no motivos automáticos de exclusión.

## 1. Resumen Ejecutivo y Dictamen de Auditoría

Se certifica la implementación completa, verificación y aseguramiento de calidad del **Motor de Revalidación Programada y Ciclo de Vida del Catálogo (`TASK-R6-02`)** para el producto Velora.

El motor resuelve la gestión del ciclo de vida y la frescura continua de las oportunidades activas en el catálogo canónico (`data/opportunities.seed.json` y `data/opportunities.json`) y en la bandeja de staging (`data/candidates/inbox.local.json`), implementando la **Regla de Dos Verificaciones Consecutivas (*Two-Absence Rule*)**. Esta regla garantiza que una oportunidad no sea cerrada precipitadamente por un fallo transitorio de red o por una caída momentánea en el ATS, pero asegura que si desaparece durante dos ejecuciones exitosas consecutivas o si la fuente oficial confirma su cierre, pase de forma determinista y auditable a estado histórico (`opportunityStatus: "closed"`, `publicationStatus: "historical"`, `verificationStatus: "stale"`).

- **Persistencia de estado:** `data/revalidation-state.json`, desacoplando el conteo de ausencias de la estructura pública del catálogo Schema 2.

## 2. Arquitectura de la Regla de Dos Verificaciones Consecutivas

```
                                [ Oportunidad Activa en Catálogo Canónico ]
                                                     │
                                                     ▼
                                    [ Consulta a Fuente Oficial ATS ]
                                                     │
                    ┌────────────────────────────────┼────────────────────────────────┐
                    ▼                                ▼                                ▼
         [ Vacante Presente ]             [ Vacante Ausente en ATS ]         [ Error de Red / HTTP ]
                    │                                │                                │
                    ▼                                ▼                                ▼
         ¿Explícitamente Cerrada?            ¿Conteo Ausencias?            (5xx / 429 / 403 / Timeout)
         ┌──────────┴──────────┐            ┌────────┴────────┐                       │
        SÍ                     NO          = 1               >= 2                     ▼
         │                      │           │                 │             [ TEMPORARY_ERROR ]
         ▼                      ▼           ▼                 ▼             - Contador NO sube
  [ CLOSED_CONFIRMED ]  [ OPEN_CONFIRMED ]  [ DISAPPEARED_    [ NOT_FOUND_  - Vacante se preserva
  - Pasa a histórico    - Reset ausencias:  ONCE ]            CONFIRMED ]   - Cero cierres ciegos
  - Con evidencia         conteo = 0        - conteo = 1      - conteo = 2
  - Sin esperar 2 aus.  - Actualiza TTL     - SALVAGUARDA:    - Pasa a histórico
                        - Permanece activa    SIGUE ACTIVA    - Cierre certificado
```

### Taxonomía de Estados y Respuestas Semánticas

| Código de Resultado | Significado Semántico | Acción sobre el Catálogo | Modificación de Ausencias |
|---|---|---|---|
| `RESULT_OPEN_CONFIRMED` | Vacante confirmada activa y vigente en el ATS oficial. | Actualiza `lastVerifiedAt` y `lastCheckedDate`. Permanece activa. | Reinicia contador a 0. |
| `RESULT_DISAPPEARED_ONCE` | Vacante no encontrada en una primera verificación exitosa. | **Ninguna (Salvaguarda activa)**. Permanece activa en catálogo. | Incrementa contador a 1. |
| `RESULT_NOT_FOUND_CONFIRMED` | Vacante ausente en 2 verificaciones consecutivas exitosas. | Transición a `closed` e `historical`. Registra nota de decisión. | Se mantiene en 2 (cerrada). |
| `RESULT_CLOSED_CONFIRMED` | El ATS reporta explícitamente estado "cerrado" o "concluido". | Transición directa a `closed` e `historical` con evidencia. | Registrado en histórico. |
| `RESULT_TEMPORARY_ERROR` | Fallo de red, HTTP 403/429/500, timeout o JSON malformado. | **Ninguna (Salvaguarda anti-cierre)**. Estado preservado. | **NO se altera el contador**. |
| `RESULT_SOURCE_UNSUPPORTED`| Fuente sin conector automatizado disponible o no autorizada. | Preservada sin modificación. Reportada para inspección manual. | No aplica. |
| `RESULT_UNKNOWN` | Oportunidad sin identificador de requisición deducible. | Preservada sin modificación. Reportada como no verificable. | No aplica. |

## 3. Persistencia de Estado y Protección de Concurrencia

### 3.1 Almacenamiento de Estado Desacoplado (`data/revalidation-state.json`)
Para evitar sobrecargar las fichas públicas de oportunidades con metadatos volátiles de monitoreo de red, Velora mantiene el estado de ausencias y trazabilidad en un archivo dedicado:
```json
{
  "lastRunAt": "2026-11-25T16:31:42-05:00",
  "opportunities": {
    "OP-006": {
      "opportunityId": "OP-006",
      "sourceId": "greenhouse-canonical",
      "requisition": "8379825",
      "employer": "Canonical",
      "consecutiveMissingCount": 0,
      "firstAbsentAt": null,
      "lastAbsentAt": null,
      "lastCheckedAt": "2026-11-25T16:31:42-05:00",
      "lastResult": "OPEN_CONFIRMED",
      "history": [
        {
          "timestamp": "2026-11-25T16:31:42-05:00",
          "result": "OPEN_CONFIRMED",
          "asOf": "2026-11-25",
          "note": "Vacante confirmada activa en ATS oficial."
        }
      ]
    }
  }
}
```

### 3.2 Bloqueo de Concurrencia (`RevalidationLock`)
- Ubicación: `data/.revalidation.lock`
- Registro atómico de `pid`, `timestamp` y marca ISO.
- Timeout de seguridad de 600 segundos para liberación automática en caso de finalización anormal del proceso.
- Mecanismo contextual (`with RevalidationLock(): ...`) que garantiza liberación segura en bloques `finally`.
